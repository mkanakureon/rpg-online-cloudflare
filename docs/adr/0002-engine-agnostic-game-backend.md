# ADR 0002: RPG 専用から、エンジンに依存しないモジュール式のゲームバックエンドへ

- **日付:** 2026-10-30
- **状態:** 採用
- **元の検討:** `docs/inspecs/2026/10/共通ゲームバックエンド構想 — Cloudflare基盤の拡張設計.md`
- **置き換えるもの:** `docs/guides/decisions/feature-study.md` の「1. 目的」の UE 製 RPG 制作ツール専用という位置づけ。ADR 0001 の「Mac で先にサーバーを作り、CLI モックを唯一の初期クライアントにする」はそのまま有効

## 背景

このリポジトリは UE 製 RPG 制作ツールにオンライン機能を足すサーバーとして始めた。お知らせ・ランキングのように、作ろうとしている機能の多くはジャンルにもエンジンにも依存しない。2 作目以降のゲームでも、別のサーバーを作らずに同じものを使いたい。

## 決定

- 目的を「**Cloudflare 上で動く、エンジンに依存しないモジュール式のゲームバックエンド**」にする。RPG に限らず、OSS として公開することを目指す。
- 対象のクライアントは **Unreal・Unity・ブラウザ（TypeScript）の 3 つ**に絞る。どれも HTTPS / JSON の同じ API を呼ぶ。
- **いまのクライアントは CLI モック（`scripts/cli-mock.mjs`）だけ。** 3 つのクライアントの実装は Phase 3 で行う。それまではサーバー側の実装を進める。
- 運用は「**共通のコードを、ゲームごとに別々にデプロイする**」形を基本にする。複数のゲームを一つでホストする形は、必要になってから足す。そのため、いまは `tenant_id` を持たない（デプロイが 1 テナントにあたる）。テーブルには必ず `game_id` を持たせる。
- 構成は、一つの Worker の中を機能ごとに分ける（`src/core/` と `src/modules/<機能>/`）。モノレポ（`apps/` `packages/`）には、二つ目の使い手（管理画面など）ができた時に切り出す。
- ゲームごとに、使う機能を登録時に選べるようにする。この設定は使える機能を決めるだけで、認証・認可の代わりにはならない。
- ゲーム固有のルール（戦闘の計算・レシピなど）は共通のサーバーに入れない。共通にするのは、セーブ・所持品・報酬の付与のような仕組みだけ。
- P0 は、ゲームの登録・アカウント（ゲストの最小形）・セーブ・設定配信・お知らせ・ランキング。作る順は、ゲームの登録 → アカウント → セーブ → 設定配信 → 既存の 2 機能を新しい土台へ移す。
- リポジトリの名前は当面変えない。名前の変更とライセンス（MIT を推す）は、公開する時に決める。

## 理由

- エンジンに依存しない HTTP/JSON の境目は、すでに ADR 0001 で作ってある。目的を広げても、いまのコードを捨てずに済む。
- アカウントを先に作れば、セーブを「送られてきた `playerId` を信じる」形で作って、後から契約を壊すことを避けられる。
- ゲームごとに別々にデプロイすれば、マルチテナントの運用の手間（データの隔離・課金・サポート）を、必要になるまで背負わずに済む。

## トレードオフ

- CLI モックだけでは、各エンジンの HTTP の癖（タイムアウト・非同期・保存先）を確かめられない。Phase 3 でクライアントごとに試す。
- 3 つ以外の配信先（YouTube Playables のように外部への通信を禁じる所など）は対象にしない。必要になったら別の ADR で決める。
- 共有ホスティングを後から足す時は、`tenant_id` の列とアクセス制御の追加が要る。
